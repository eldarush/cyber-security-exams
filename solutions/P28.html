SQL injection — הפרדת ערך ממבנה שאילתה

סדר החלופות מתערבב בכל פתיחת עמוד. המפתח המוצג מתאים לסדר הנוכחי. אותיות בתוך הסברים מיובאים מתייחסות לשאלון המקורי — יש לזהות את התשובה לפי תוכנה.

P28 · אבטחת Web

איזו פעולה היא ההגנה הישירה ביותר מפני SQL injection כאשר ערך שהמשתמש מסר צריך להיכנס לתנאי WHERE?

  1. א. הגדרת X-Frame-Options ללא שינוי השאילתה.
  2. ב. מחיקת המילה union פעם אחת מן הקלט.
  3. ג. שאילתה עם פרמטר קשור, כך שהערך מטופל כנתון ולא כתחביר SQL.
  4. ד. בדיקת JavaScript בדפדפן בלבד.

התשובה הנכונה כאן: ג. שאילתה עם פרמטר קשור, כך שהערך מטופל כנתון ולא כתחביר SQL.

דרך הפתרון

בשאילתה פרמטרית מבנה ה-SQL נשאר בשליטת היישום, וערך המשתמש נמסר כנתון דרך ממשק הקישור. לכן גרש או מילה שנראית כמו SQL בתוך הערך אינם אמורים להפוך לתחביר חדש. השאלה עוסקת בערך בתנאי WHERE, שמתאים לפרמטר, ולא בשם טבלה או עמודה.

SQL structure: SELECT ... WHERE user_name = ?
Bound value:   the supplied user-name string

למה התשובה נכונה ולמה שאר האפשרויות שגויות

מזהים כל חלופה לפי הטקסט שלה; אותיות התשובות משתנות בערבוב.

נכונה — שאילתה עם פרמטר קשור, כך שהערך מטופל כנתון ולא כתחביר SQL.

פרמטר קשור מפריד בין הערך לבין מבנה הפקודה. כך ערך כגון מחרוזת עם גרש נשאר ערך להשוואה ואינו סוגר מחרוזת ומוסיף תנאי לשאילתה.

שגויה — מחיקת המילה union פעם אחת מן הקלט.

מתקפות SQL injection אינן חייבות להשתמש במילה union. סינון נקודתי של מילה אחת אינו מפריד נתונים מתחביר וניתן לעקיפה בדרכים תלויות הקשר.

שגויה — בדיקת JavaScript בדפדפן בלבד.

תוקף אינו חייב להפעיל את קוד JavaScript של האתר. הוא יכול לשלוח בקשה ישירה לשרת, ולכן בדיקת לקוח לבדה אינה מגינה על בניית השאילתה.

שגויה — הגדרת X-Frame-Options ללא שינוי השאילתה.

X-Frame-Options עוסק בהטמעת דף במסגרת ובסיכוני clickjacking. הוא אינו משנה את האופן שבו מסד הנתונים מפרש את פקודת SQL.

דגש והנחות שחשוב לזכור

אין לשרשר קלט לשאילתה ואז לקרוא לה ״מוכנה״: הקישור עצמו צריך לשמור על הערך כנתון. רכיבים מבניים שאינם ניתנים לפרמטריזציה דורשים בחירה מבוקרת מתוך רשימת ערכים מותרת. גם שאילתה בטוחה מהזרקה עדיין דורשת בדיקות הרשאה מתאימות.

מקורות לבדיקת המנגנון: OWASP — SQL injection prevention
